// the problem

One document, two completely different readings

Design tools make resumes that humans love and parsers hate. Here's the same resume, both sides.

👤 WHAT THE HUMAN SEES

  • A polished two-column layout with a clean sidebar
  • Skills visualized as stylish progress bars and icons
  • A beautiful timeline graphic for work history
  • Contact info tucked neatly into the page header
  • "Senior Full-Stack Engineer" title in a display font
✨ looks great — 10/10 would interview

🤖 WHAT THE MACHINE PARSES

  • "Built backend APIs Managed 5 reports" — columns fused mid-sentence
  • Skill bars = images. Zero extractable keywords.
  • Timeline dates = graphics. Career reads as 0 years.
  • Header content dropped — no email, no phone found
  • "SeniorFull-StackEngineer" — font ligatures mangled the title
⚠ auto-rejected — nobody will ever know why
// under the hood

The audit pipeline, stage by stage

Five deterministic stages — no black boxes, no magic. Every number is explainable.

📥

Upload & input st.file_uploader

Your PDF arrives as an in-memory buffer — never written to disk. The job description arrives as plain text. The audit waits for both, deliberately.

⛏

Aggressive parse pdfplumber · layout=False

Text extracted exactly the way a line-by-line ATS reader does — ignoring your careful visual positioning, just like they do.

🧹

Tokenize & filter stop-words · len > 2

Both sides lowercased and tokenized; JD noise stripped; the top-20 highest-frequency terms become the scoring targets.

🛠

Structural checks 3 heuristics

Ghost-image detection (<150 chars), multi-column back-jump detection, and machine-readable date validation — the silent killers, caught first.

📊

Score & render Jaccard coverage

Match index = fraction of JD keywords found verbatim in your text. Bands: ≥75% Safe · 50–74% Borderline · <50% High Risk.

// capabilities

Everything in the scanner, honestly labeled

What v0.2.0 does today — and the wiki documents every limit, because a checker that hides its limits is selling comfort, not insight.

📊

ATS Compatibility Score

Jaccard-style coverage of the JD's top-20 keywords, with Safe / Borderline / High-Risk bands mirroring common filter cutoffs.

🤖

Raw Text Stream

The literal string a parser extracts — merged words, scrambled columns and all. Most users see their resume honestly for the first time.

🎯

Keyword Matrix

Matched vs. missing high-value terms from the job description, so every score point is traceable to a fixable gap.

👻

Ghost-Image Detection

Design-tool exports that are really flat images parse as ~blank. Under 150 characters triggers a fatal alert before you waste an application.

📐

Multi-Column Alert

Detects the side-by-side layouts that fuse into nonsense strings like "Built backend APIs Managed 5 reports."

🗓

Timeline Validation

Verifies machine-readable date patterns (Month YYYY, MM/YYYY, Present) — unparseable timelines read as zero verifiable experience.

🔒

Privacy by Architecture

No database, no accounts, no telemetry, no network calls. In-memory only. Close the tab and it's gone — that's the guarantee.

🧩

Optional LLM Prompts

Curated, privacy-first prompt templates for synonym mapping and honest rewrites — user-keyed, never required, never auto-run.

🛰

Free Public Hosting

Stateless by design, so anyone can deploy a public instance on Streamlit Community Cloud's free tier in two minutes.

// quickstart

Run it locally in three steps

Everything you need is in the repo. Full details in INSTALL.md.

STEP 01

Clone the repository

Grab the code and step inside.

# clone & enter
git clone https://github.com/YOUR_USERNAME/FED-Indeed.git
cd FED-Indeed
STEP 02

Install dependencies

Two packages — that's the entire dependency tree.

# virtualenv (recommended) then:
pip install -r requirements.txt
STEP 03

Launch the scanner

Browser opens at localhost:8501. Upload, paste, audit.

# that's it — no keys, no config
streamlit run app.py
// roadmap

What the machine does next

Staged by impact. Community votes genuinely reorder these — full detail in ROADMAP.md.

STAGE 1 · next

Validation hardening

Fuzzy & stemmed matching ("manage" ↔ "management"), contact-info validation, user-adjustable pass threshold, JD sectioning that ignores Benefits boilerplate.

STAGE 2

Weighted & temporal scoring

Required-vs-preferred weighting, per-skill tenure extraction, and section-aware parsing that scores Work / Education / Skills separately.

STAGE 3

Depth & insight

Action-verb & impact analysis, graphics-to-text ratio checks, semantic synonym mapping via the local prompt templates, education parsing.

STAGE 4

Power users

Batch multi-JD comparison, session-local score history, DOCX input — while staying local-first, always.
